Team engineering for AI agents

Build a team of AI agents from text files. Experiment. Improve.

Each agent is a text file of plain instructions. A team is a folder. One more file, the chair, says who speaks when. TeamRunner runs the team, keeps every word, decision and cost, and lets you change one line and run it again.

Install in two commands Why a team?

Mac, Windows and Linux. OpenAI, Anthropic, Gemini, OpenRouter, or free local models through Ollama. No code.

In our six recorded runs on the motion “Splitting AI work into clear roles makes it safer and easier to audit and improve than one prompt doing it all”, for won two of three plain debates but only one of three checked ones.     Why a team, and not one big prompt?

    For the same reasons organizations don’t hire one person to do everything

    A single agent with every instruction, every tool and every document piles it all into one prompt. Splitting the work across agents lets you give each one a narrow job, the right model, only the tools it needs, and a place in a flow you can read. Each reason below comes with the organizational idea it borrows and the research behind it.

    01

    One job per agent

    A job description, not “other duties as assigned”

    Each agent’s file holds one objective in plain words. A fact checker that only checks facts can’t drift into arguing, and its instructions are short enough to read, test and fix on their own.

    Anthropic’s research agent splits work across subagents with “clearly divided responsibilities”: How we built our multi-agent research system, 2025.

    02

    Smaller contexts, steadier behaviour

    A briefing, not the whole archive

    Models get less reliable as their input grows, even on simple tasks, and miss what sits in the middle of a long prompt. In a team each agent carries only its own instructions, and a tool’s answer goes only to whoever asked: a 20,000-character web page the fact checker reads never lands in the debaters’ prompts.

    Context Rot, Chroma, 2025, 18 models; Lost in the Middle, Liu et al., 2023.

    03

    The right model for each job

    You don’t staff every desk with a senior partner

    The team names one model in team.yaml, and any agent can name its own with a model: line. Put the judge on a strong model and the drafters on a cheap or free local one, or mix providers in one team.

    Sending only the hard calls to the strong model cut cost by over 2× with little loss in quality: RouteLLM, Ong et al., 2024.

    04

    Costs you can see, and bound

    A budget line for each department

    Every turn records its tokens and cost, by agent. Every loop must carry a count, so a run always ends. A toolkeeper caps calls per turn. A missing key stops the run before anything is spent, and a rehearsal costs nothing at all.

    Teams of agents can burn through tokens fast, and token use alone explained 80% of the variance in Anthropic’s results, so measure it: Anthropic, 2025.

    05

    Guardrails where the tools are

    The tool crib, not a power drill on every desk

    Agents never hold tools. A toolkeeper does, with a plain access list: who may use it, how often, with what limits. The sandbox runs Python with no internet. TeamRunner enforces the terms, not the agent’s good behaviour.

    Least privilege for agents is the standard fix for “excessive agency”: OWASP Top 10 for LLM Applications, LLM06, 2025.

    06

    A flow you can read, control and change

    The meeting rules, written down

    Who acts next is a script in chair.md, drawn as a diagram. Decisions are typed answers, like pass or fail, and there are no hidden if-statements. To change how the team works, you change a line.

    Most failures of multi-agent systems trace to how the system is designed, specs and hand-offs, not only to the model: Why Do Multi-Agent LLM Systems Fail?, Cemri et al., NeurIPS 2025.

    07

    Checks and balances

    Separation of duties: the writer isn’t the editor

    The agent that makes a claim isn’t the one that checks it. A fact checker can send a speech back; a judge hears both sides and the checker’s verdicts before ruling.

    Models that debate and check each other got more factual and reasoned better: Improving Factuality and Reasoning through Multiagent Debate, Du et al., 2023.

    08

    Information where it belongs

    Need to know

    A fact can live in one member’s own file, so only that member knows it until they choose to share it. That is how the hiring committee below works. Sealing whole conversations from some members is coming next.

    The classic hidden-profile study of groups: Stasser & Titus, 1985.

    09

    Every step on the record

    Minutes for every meeting

    Each run keeps its own folder on your disk: every prompt and reply, every decision about who acts next, every tool call, the model that answered, tokens, time and cost. Compare two runs side by side. No agent can read or change the record.

    You can only fix a hand-off you can see. Plain files, no dashboard to log in to.

    10

    Improve by experiment, not by hunch

    Pilot it, then make it policy

    A team isn’t automatically better than one agent; studies find the gains are often small. So treat the structure as a hypothesis: change one line, rehearse for free, run both versions a few times, and compare.

    Gains over single agents “often remain minimal” on popular benchmarks: Cemri et al., 2025. That is the case for testing.

    Tutorial

    Install, then nine steps, each on a team that ships with TeamRunner

    Each step starts from a working example and adds one idea. Follow it in your browser or in a terminal. Every step can be rehearsed for free before you spend anything; a real run costs a fraction of a cent.

    2. 1RehearsefreeCopy round_robin and run it with no model.

    The big example · hiring_committee

    Every fact the committee needs is in the room. Does it find them?

    In 1985 Stasser and Titus showed that human groups mostly discuss what they all already know, and so miss the facts that would change their decision. It is one of the most replicated findings about how groups decide. With TeamRunner you can ask whether a committee of AI agents falls into the same trap, and what gets it out. It ships as an example, so you can run it today.

    The task

    Three members, three candidates, and facts no one person has

    The committee is hiring a Director of Operations for a food bank. Everyone has read the same packet, which makes Avery look best. Each member also holds two facts the others don’t, written into that member’s own file.

    Alone, each member would still choose Avery. With all six facts on the table, Blake is the clear choice.

    What everyone knowsteam.yaml
    Avery12 years · ran a $20M budget · strongest interview · MBA · under budget three years running
    Blake6 years, at one food bank · promoted twice · never managed more than $3M · halting interview
    Casey9 years in retail logistics · bilingual · no nonprofit experience
    What only one member knowseach member’s own file

    chen.md reference calls

    Avery Former manager would not say whether they would rehire.

    Blake “The best operations person I have worked with.”

    diaz.md finance office

    Avery Part of one under-budget year came from a one-time grant.

    Blake Cost per meal delivered fell 18% in two years.

    okafor.md human resources

    Avery Team turnover 28%, against 18% across the sector.

    Blake Regular volunteers grew from 250 to 400.

    The change

    Change how the meeting is run: swap one line for another

    A well-known fix from the research is to have everyone report what they know before anyone gives an opinion. In TeamRunner the way a meeting runs lives in one file, chair.md. Both versions are already written there. Put a # in front of one and take it off the other. Nothing else changes.

    chair.mdopen discussion → share first
    # How the meeting is run. This is the line the experiment changes.
    - meeting(*3) -> clerk:record
    + # meeting(*3) -> clerk:record
    - # chen:share_facts -> diaz:share_facts -> okafor:share_facts -> meeting(*2) -> clerk:record
    + chen:share_facts -> diaz:share_facts -> okafor:share_facts -> meeting(*2) -> clerk:record
    meeting = chen -> diaz -> okafor
    Red is the old line, green the new one: this view of a change is called a diff. A line starting with # is a note for people, and is not run.
    The run

    Run both versions, a few times each, and compare

    Every turn records whom each member would hire right now, so you can see when minds change and whose facts changed them. Models are random, so run each version more than once; teamrunner runs lists every run with the committee’s decision.

    Running each version 25 times and getting one table is coming soon. Tutorial step 8 does it by hand today.

    Planning a study? Here is what comes next

    Designed experiments

    One file names the versions to compare and how many runs of each. TeamRunner runs them all, seeded, and gives you one CSV for R, Stata or pandas.

    Who sees what

    Seal reviewers from each other, or pass work along a chain where each person hears only the one before. One line each, in a whiteboard file.

    Managers

    An AI that runs the meeting and decides who speaks next, in place of a fixed script, so script vs. judgment can itself be compared.

    Subteams

    A folder inside a folder: a subcommittee that deliberates on its own and reports back, so the org chart is the directory tree.

    Glossary

    The words, in plain English

    API key
    A password-like code from a model provider that lets TeamRunner use its models. The provider bills you for what you use. Rehearsals need none.
    chair
    The file chair.md: the meeting’s script, saying who speaks when. With no chair, members take one turn each, in name order.
    context
    Everything a model reads before it answers: its instructions plus what has been said. Smaller is cheaper and usually steadier.
    diff
    A view of what changed between two versions of a file: removed lines in red, added lines in green.
    frontmatter
    The settings block between the two --- lines at the top of an agent’s file.
    git
    Version control: it keeps every saved version of a folder, so you can go back, see what changed, or share it. Optional.
    Markdown
    Plain text with light formatting, in a file ending .md. An agent is one.
    rehearsal
    A run with no model: placeholder words and random answers. Free, needs no key, and shows whether the flow goes where you meant.
    replications
    How many times each version is run. Models are random, so one run is an anecdote.
    side trip
    A member asking a toolkeeper during its own turn, when it chooses. Not a step in the flow; the answer goes to that member alone.
    terminal
    The window where you type commands: Terminal on a Mac, PowerShell on Windows.
    toolkeeper
    A member with no model that holds one tool, such as reading the web, and decides who may use it and how often.
    uv
    A single program that installs Python for you and runs Python tools, each in its own space. It is how we suggest installing TeamRunner.
    YAML
    A plain-text format for settings, one name: value per line. team.yaml is one.

    teamrunner

    Preview release. Until the first announced release, a new version may need changes to teams made with an earlier one.
