Teams of AI agents, for people who study organizations

Build a team of AI agents from text files. Change one line. Run it again.

Each agent is a text file in plain words, and a team is a folder. No code and no framework to learn. Try the whole flow for free in a rehearsal, then run it for real and keep every prompt, reply and cost.

Start from a sentence

Describe your team in a sentence, and TeamRunner writes the files

Say who is on the team and how they work together. A model writes the files, TeamRunner checks them and has any mistakes fixed, then shows you the team and draws its flow. Every file is plain text you can read and change.

A question from the study of groups

When the key facts are spread across a committee, does it pick the best candidate?

In 1985 Stasser and Titus showed that human groups mostly discuss what they all already know, and so miss the facts that would change their decision. It is one of the most replicated findings about how groups decide. With TeamRunner you can ask whether a committee of AI agents does the same, and what fixes it. It ships as an example, so you can run it today.

The task

Three members, three candidates, and facts no one person has

The committee is hiring a Director of Operations for a food bank. Everyone has read the same packet, which makes Avery look best. Each member also holds two facts the others don't, written into that member's own file.

Alone, each member would still choose Avery. With all six facts on the table, Blake is the clear choice.

The change

Change how the meeting is run: swap one line for another

A well-known fix from the research is to have everyone report what they know before anyone gives an opinion. In TeamRunner the way a meeting runs lives in one file, chair.md, the team's chair. Both versions are already written there. Put a # in front of one and take it off the other. Nothing else changes.

chair.mdopen discussion → share first
# How the meeting is run. This is the line the experiment changes.
- meeting(*3) -> clerk:record
+ # meeting(*3) -> clerk:record
- # chen:share_facts -> diaz:share_facts -> okafor:share_facts -> meeting(*2) -> clerk:record
+ chen:share_facts -> diaz:share_facts -> okafor:share_facts -> meeting(*2) -> clerk:record
meeting = chen -> diaz -> okafor
Red is the old line, green the new one: this view of a change is called a diff. A line starting with # is a note for people, and is not run.
The run

Run both versions, a few times each, and compare

Every turn records whom each member would hire right now, so you can see when minds change and whose facts changed them. Models are random, so run each version more than once; teamrunner runs lists every run with the committee's decision.

Try it in 5 minutes

Rehearse a team first. No key, no cost.

Install TeamRunner, open it in your browser, copy an example and rehearse it. A rehearsal runs the whole team with no model, so it is free and needs no account anywhere. You need a terminal only to install TeamRunner and start it; the rest happens in your browser, on your own computer.

The installer, uv, fetches the right version of Python on its own, so you don't need Python first.

  1. Open Terminal (press ⌘ Space, type “Terminal”) and install uv:curl -LsSf https://astral.sh/uv/install.sh | sh
  2. Close Terminal, open it again, then install TeamRunner:uv tool install teamrunner
  3. Open TeamRunner in your browser:teamrunner ui
  4. Choose New team, call it hello and start from round_robin. Then Run… and Rehearse team. If it says completed, it works.

Tutorial

Nine steps, each on a team that ships with TeamRunner

Each step starts from a working example and adds one idea. The first is free; after that, every step can still be rehearsed for free before you spend anything.

  1. 1RehearsefreeCopy round_robin and run it with no model.
  2. 2Your first real runAdd a key, give it your own topic, open what it kept.
  3. 3Edit the wordsMake the critic aggressive, run again, compare the two runs.
  4. 4Take control of the flowAdd a chair and rounds, and see the flow drawn.
  5. 5Typed answers and decisionsThe judge’s winner, then a fact checker that sends a speech back.
  6. 6ToolsReading the web, through a toolkeeper, on terms you set.
  7. 7Private informationThe hiring committee: facts only one member knows.
  8. 8A first experiment, by handOpen discussion vs. share first, five runs each, and a tally.
  9. 9Bigger organizationsA code review by five engineers, and a reference checker.

Concepts

Five ideas cover the whole format

An agent is a Markdown file

Settings at the top, between two --- lines (the frontmatter), and below them the agent’s instructions in plain words. Edit it in any text editor.

judge.md

A folder is a team

Any folder with a team.yaml is a team, and the file browser is the org chart. YAML is just settings, one per line.

team.yaml

Every team has a chair

Someone always decides who speaks next: the script in chair.md, or, with no chair file, members in name order. Every decision is logged.

chair.md

Tools sit with a toolkeeper

A toolkeeper holds a tool, such as reading the web, and decides who may use it, on what terms. Agents never hold tools themselves.

web.md

Every run is kept

Each run gets its own folder on your disk with everything that happened, so two runs can be compared line by line.

runs/

What every run keeps

A run folder is a full record, on your own disk

Plain files you can open and compare. No dashboard you have to log in to, and no agent can read or change the record.

runs/2026-10-12_143201_debate/
runs/2026-10-12_143201_debate/
├── output.md     ← what the team produced: open this first
├── run.json      ← when, what, versions, cost
├── events.jsonl  ← every turn, one line each
├── inputs/       ← copies of files it was given
└── work/         ← what its code wrote
Every prompt and every reply
Exactly what each agent could read, what it said, which model answered, tokens, cost and time.
Every decision about who acts next
Who made it and why. There are no hidden if-statements.
Every tool call
Who asked, whether the toolkeeper said yes, and what came back.
The exact version that ran
Your 2026 study can be rerun in 2028. Put the team folder in git or zip it, and it is a replication package.

Built for research Coming soon

Describe both versions in one file, run each 25 times, get one CSV

One run is an anecdote, because models are random. Soon an experiment file will sit beside your team, name the versions to compare, and say how many replications of each to run, with one seed. Each version is a patch, and the file is an overlay: your team stays clean and runnable. You get one CSV for R, Stata or pandas.

What’s coming

Planning a study? Here is what comes next

Nothing on this list is in TeamRunner yet, and none of it is in the tutorial. What you build today keeps working as these arrive.

Designed experiments

One file names the versions to compare and how many runs of each. TeamRunner runs them all, seeded, and gives you one CSV.

Who sees what

Seal reviewers from each other, or pass work along a chain where each person hears only the one before. One line each, in a whiteboard file.

Managers

An AI that runs the meeting and decides who speaks next, in place of a fixed script, so script vs. judgment can itself be compared.

A run browser

Open a run, or two side by side, and read it turn by turn in your browser. The files on your disk stay the record.

Glossary

The words, in plain English

API key
A password-like code from a model provider that lets TeamRunner use its models. The provider bills you for what you use. Rehearsals need none.
chair
The file chair.md: the meeting’s script, saying who speaks when. With no chair, members take one turn each, in name order.
diff
A view of what changed between two versions of a file: removed lines in red, added lines in green.
frontmatter
The settings block between the two --- lines at the top of an agent’s file.
git
Version control: it keeps every saved version of a folder, so you can go back, see what changed, or share it. Optional.
Markdown
Plain text with light formatting, in a file ending .md. An agent is one.
overlay
A file that sits outside a team and changes it for one study, without editing the team. Coming soon.
patch
A small change applied to a copy of the team for one version of an experiment. Coming soon.
rehearsal
A run with no model: placeholder words and random answers. Free, needs no key, and shows whether the flow goes where you meant.
replications
How many times each version is run. Models are random, so one run is an anecdote.
seed
A number that fixes the random choices TeamRunner makes, so the same seed gives the same plan.
terminal
The window where you type commands: Terminal on a Mac, PowerShell on Windows.
toolkeeper
A member with no model that holds one tool, such as reading the web, and decides who may use it and how often.
YAML
A plain-text format for settings, one name: value per line. team.yaml is one.
