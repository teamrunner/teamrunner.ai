experiment.md

An experiment runs versions of a team side by side, many times each, in a fair order, and counts the results the same way for every version. It is one file, experiment.md, in a folder of its own. The team it studies is never edited.

A first experiment

Does the model playing the advocate change who wins the debate? Make a folder in your workspace's experiments/, and in it this file:

experiments/advocate_model/experiment.md
---
name: advocate-model
conditions:
  gpt:
    from: debate
    change:
      advocate.model: openai/gpt-6-luna
  claude:
    from: debate
    change:
      advocate.model: anthropic/claude-sonnet-5-5
replications: 20        # 2 conditions × 20 = 40 runs
seed: 42
metrics:
  - judge.output.winner
limits:
  max_concurrent: 4
  max_cost_usd: 40.00
---

## Question

Does the model playing the advocate change who wins the debate?

It names two versions of the team debate, called conditions. Each starts from: the team and says what to change: in it; here only the advocate's model differs. Each condition runs 20 times, in an order drawn from seed: 42, and every run's judge's answer is counted. The text below the settings is for people: every run records it.

Try it, spending nothing:

teamrunner experiment advocate_model --plan # the conditions, how they differ, the order, the cost estimateteamrunner experiment advocate_model --rehearse # every run end to end, with no model, at no costteamrunner experiment advocate_model # the real runs

In teamrunner ui, the same experiment is under Experiments. A shipped example uses everything on this page: teamrunner new my_study --from leader_vs_flat. New in 0.0.7.

The rest of this page is every setting in detail.

The folder

A folder is an experiment when it holds experiment.md. Beside it live the study's own files:

experiments/leader_vs_flat/
experiments/leader_vs_flat/
├── experiment.md
├── variants/        files a condition puts in place of the team's
├── metrics/         answer keys (.yaml) and evaluators (.md); no member ever reads them
├── tasks/           the inputs every condition gets
├── conditions/      built by TeamRunner, rebuilt before every run
└── runs/            one folder per run

Only experiment.md is needed. The experiment must be outside the team it studies: an experiment folder inside the team's package is refused, so nothing it makes lands in the team.

The settings block

The settings go at the top, between two lines of ---. A file that does not start that way is refused. Any word the file does not know is refused with the nearest known word (replicates → did you mean replications?), and two old words say what replaced them: patch: is now change:, and conditions_order: is gone because the order is drawn from seed:.

Setting Needed What it is
name yes A short name for the experiment
conditions this, or base and factors Each version, by name
base and factors this, or conditions Every combination of several changes
replications yes Runs per condition, at least 2
allow_single_run no true lets replications: 1 through
seed yes Fixes the order of the runs and each run's seed
task no The inputs every condition gets
metrics no What to measure, besides cost and time
limits no Runs at once, and the ceiling on estimated cost

name:

Any short text: name: advocate-model. It is shown at the top of the console, the summary and the page. Changing it does not change the study.

conditions:

The simple form. Each line under it is one condition: its name, then the team it runs.

experiment.md
conditions:
  control: debate                 # the team as it is
  bold:
    from: debate
    change:
      advocate.prompt: file:variants/bold.md
  • A team alone (control: debate) runs that team as it is: the control, written like any other condition. from: with change: {} or no change: at all is the same.
  • from: and change: run the team with the changes applied. A condition has only these two words; anything else is refused.
  • Where the team is. A name with no slash (debate) is a team in your workspace's teams/ (and, when the experiment is in a workspace's experiments/, in the teams/ beside it). Anything else is a path from the experiment's folder (../../teams/debate), or from your home folder if it starts with ~. The folder must hold a team.yaml. A single member's .md file is refused: TeamRunner runs team folders so far.
  • Names. A condition's name becomes a folder's name, so it uses letters, digits, _ and -. Names Windows will not give a folder (con, nul, com1, …) are refused, and so are two names that differ only in capitals (Short and short), because macOS and Windows would make them one folder. New in 0.0.7.

change:

What a condition changes in its team. One line per change: what, then its new value.

You write It changes The value is
advocate.model: openai/gpt-5 one setting of the member advocate the new value
advocate.params.temperature: 0.2 a setting inside a setting the new value
advocate.prompt: file:variants/bold.md the member's prompt, the text below its settings file: a file with the prompt only
judge: file:variants/strict_judge.md the whole member file, or adds a member the team lacks file: a whole member file
fact_checker: remove takes the member out of this condition remove
chair: file:variants/chair_leader.md the whole flow (chair.md) file:, or remove
models/careful: file:variants/careful.yaml a whole model profile in the team's models/ file:, or remove
  • file: names a file in the experiment's folder, by its path from there, usually in variants/. A file outside the experiment's folder is refused.
  • Only the team's own files. A change with .., a backslash or a path from the top of the disk, or one that would land outside the condition's copy of the team, is refused, and a change never writes or deletes through a link. New in 0.0.7.
  • A setting is any of a member's settings except id and parent_id, which say who a member is, not how it works. A misspelled member or setting is refused with the nearest match (emmma.prompt → did you mean emma?). A setting is changed only on a member the team has; to add a member, add the whole file.
  • A setting from a file. advocate.description: file:variants/long.txt gives the setting the file's text.
  • remove takes out a whole file. advocate.model: remove is refused: give the setting its new value instead.
  • A prompt file holds the prompt only. One that starts with a settings block is refused; to change the settings too, change the whole member.
  • Whole files first. Whole-file changes are applied before setting changes, so judge: file:… and judge.model: … together give the new judge that model.
  • Not yet. Changes to whiteboard, to manager.md, and to teams inside teams (subteam/member.model) come in a later version of TeamRunner; --plan says so and runs nothing.

After the changes, every condition is checked as a whole team, as teamrunner validate would, and its problems are shown at their file and line.

Conditions are folders. A condition with changes is built as a complete team under conditions/<name>/, marked by a GENERATED.md note, and rebuilt before every run. You can open it, rehearse it or run it alone, but an edit made there is lost: change experiment.md or the files in variants/ instead. A folder under conditions/ without that note was not made by TeamRunner and is never replaced; the condition that would be built there is refused until you move it.

base:

The full form, for several changes at once. base: is the team every condition starts from, written as in conditions:. It always comes with factors:, and a file may not have both conditions: and base:.

factors:

Each factor is one thing you vary, with its levels. Every combination of levels is a condition.

experiment.md
base: orchestrators_lite
factors:
  leader:
    - label: flat
      change: {}
    - label: visible
      change:
        chair: file:variants/chair_leader.md
  model:
    - label: small
      change: {emma.model: openai/gpt-5-mini}
    - label: large
      change: {emma.model: openai/gpt-5}

This makes four conditions: flat+small, flat+large, visible+small, visible+large. Each condition is named by its levels, joined with +, and runs.csv keeps each factor's level in a column of its own (factor_leader, factor_model). New in 0.0.7.

  • A level has label: and change:, and nothing else. Without a label it is named <factor>_<n> (model_2).
  • Labels use letters, digits, _ and -. A label that YAML reads as yes or no (no, off) must be quoted: label: "no". A number (label: 2) is read as the label 2. New in 0.0.7.
  • Two levels of one factor may not share a label, or differ only in capitals. New in 0.0.7.
  • One thing may be changed by one factor only: two factors that both change emma.model are refused.

replications:

How many times each condition runs: a whole number, at least 2. The experiment makes conditions × replications runs. One run per condition says little about a model that answers differently each time, so replications: 1 is refused unless allow_single_run: true is beside it.

Raising replications: later adds rounds and keeps the runs already made; lowering it counts the first runs and keeps the rest on record, counting them again if you raise it. New in 0.0.7. Neither changes the study.

allow_single_run:

true or false (default false). true lets replications: 1 through.

seed:

A whole number, 0 or more. It fixes everything TeamRunner controls: the order of the runs and each run's own seed. It cannot make a model answer the same way twice; it makes the design the same every time.

The runs go in rounds. Each round runs every condition once, in an order drawn from the seed, so if anything stops the experiment early, the conditions are at most one run apart. --plan shows the order. Changing the seed changes the study.

task:

A task file, by its path from the experiment's folder (usually in tasks/), with or without its ending: task: tasks/order_summary. It gives every condition the same inputs, in place of the team's default_inputs:, so editing the team cannot change the task. See a task file.

Without task:, each condition uses its team's default_inputs:. With it, an input the task leaves out comes from the team's defaults. The task may not give an input that no prompt in a condition uses, and every input a prompt uses must come from the task or the defaults.

metrics:

A list of what to measure. Cost and time are always measured. Each line is one of two things:

  • A member's typed answer, by its path: judge.output.winner. Its last answer in each run is measured as it is: a choice as the share of each answer, a number as its mean, a yes-or-no as the share of yes. The member must declare that field under its output:. A text answer cannot be counted and is refused: grade it with an evaluator.
  • A file, by its path from the experiment's folder, with or without its ending: metrics/bugs_found. An answer key (.yaml) scores against a known answer, with no model. An evaluator (.md) is a model that grades each run with a rubric, without being told which condition it came from.

Members never see metrics/, no change: reaches it, and the same metrics score every condition. Editing a metric does not change the study; it rescores the runs already made (an answer key at once and for free; an evaluator when you ask, with --evaluate).

limits:

Two settings, both optional.

  • max_concurrent: how many runs at once, a whole number, 1 or more (default 1). Keep it inside your provider's rate limits.
  • max_cost_usd: the ceiling on the whole experiment's estimated spending, running and evaluating, in dollars: 40.00. It must be more than 0.

The ceiling works on estimates at list prices. Before every model call, TeamRunner sets aside the most that call can cost; a call that does not fit what is left is not sent, and that run stops. If the estimate for the whole experiment is over the ceiling, nothing starts. It is not a cap on your provider's bill. --max-cost <usd> replaces it for one session.

Without max_cost_usd:, the command line warns that nothing caps the spending, and the page will not start a run unless every model the experiment uses is free. A rehearsal has no ceiling.

The body

Everything below the second --- is for people: the question, the hypothesis, where the idea came from. It is optional, plain Markdown. Every run records it, so a run's record shows what the hypothesis said when it ran. It is not part of the study, so fixing a typo costs nothing.

What changes the study

TeamRunner keeps a fingerprint of each condition: its built team, its inputs and the seed. Comments, spacing, id: lines, the body, name:, metrics:, limits: and replications: are left out of it.

When a fingerprint changes after runs were made, the command stops before running anything and says what changed. --restart starts the changed study from round 1; --keep-unchanged keeps the runs of conditions that did not change. Earlier runs are kept in runs/ either way, and undoing the edit makes them count again.

Editing a team while its experiment runs stops it: each run's copy of the team is checked first, and on a difference no more runs start. The runs so far are kept, and the next command says what changed. New in 0.0.7.

Keys in the file

experiment.md goes into every run's record, so the experiment's folder is checked for API keys like a team's, and a key found there is refused. New in 0.0.7.
