chair.md

chair.md says who acts when: the team's flow, written as a short script. It runs with no model, so every run follows the same script and every routing choice is logged. It is optional: without it, members take one turn each.

A first chair

The debate from the tutorial has three members, advocate, critic and judge. Give it rounds: add chair.md to the team with these lines.

# Three rounds of advocate and critic, then the judge decides.

rounds(*3) -> judge

rounds = advocate -> critic

The first line after the note is the flow: run rounds three times, then the judge. The last line says what rounds is: the advocate, then the critic. So the debate runs advocate → critic → advocate → critic → advocate → critic → judge.

Try it, spending nothing:

teamrunner validate debate --offline # the flow is checked with the rest of the teamteamrunner explain debate # the flow in plain words, under "Who acts when"teamrunner explain debate --diagram # the flow as a picture, in your browserteamrunner run debate --rehearse # the whole flow, with no model, at no cost

In teamrunner ui, select chair.md and choose Flow diagram; saving an edit redraws it. A shipped example has this chair: teamrunner new my_debate --from multi_agent_debate. Decisions below adds a fact checker to the same debate, the tutorial's Step 6.

The rest of this page is every part of the script in detail.

No chair: round-robin

Without chair.md, the members act one turn each, in the order of their file names, and the run ends. A number in front of a name sets the order and is not part of the name: 01_for.md, 02_against.md and 03_judge.md run in that order as for, against and judge. Toolkeepers take no turn of their own. Everyone hears everyone, as with a chair.

The file

The script is the whole file. It is plain text, not YAML, and needs no settings block.

  • Every line stands on its own. The order of the lines and their indentation are for the reader; TeamRunner uses neither. Write the main line first or last, indent a block's decisions under it or not.
  • # starts a note, to the end of its line: advocate -> critic # the order. Blank lines are ignored.
  • A line is one of three things: a line of steps, a -> b -> c, which is the main flow; a line of steps after a name, name = a -> b, which is the named block name; or a decision on its own, decider --option--> step.
  • A line starting with an arrow continues the line above it, so a long line can be broken:

advocate -> fact_checker --pass--> critic -> judge fact_checker --fail,*2--> stop

  • No settings. A settings block between two --- lines may be there but must be empty: any setting in it is refused, because the chair is only its script.

The grammar

You write It means
judge A turn for the member judge, or the block judge
judge:verdict The judge's turn, at the stage verdict
a -> b a, then b
rounds = a -> b The block rounds is a, then b
rounds(*3) rounds, exactly three times
checker --fail--> writer When the checker answers fail, go to writer
checker --pass,*3--> done On pass, or the third time, go to done
done, stop End this block; end the whole run
# … A note for the reader
judge -> web -> judge:verdict The judge asks the toolkeeper web, and reads the reply at its next turn

Steps

A step is a member's name, which is its file name (judge for judge.md), or a block's name. Names are letters, digits and underscores. A name that is neither a member nor a block is refused with the nearest one (critc → did you mean critic?). done, stop, others, everyone, standard and deny are words TeamRunner uses, so no member may have them as names.

Stages

member:stage gives a turn a label: judge:research, judge:verdict. The member is told the stage at its turn ("It is your turn. Stage: research."), so its prompt can say what to do at each, and the stage is recorded with the turn. A stage belongs to a member's turn: a block with a stage (rounds:x) is refused.

A member may take several turns in one flow (judge:open -> rounds(*3) -> judge:close). When a line joins at one of them, or a decision names one, give each turn a stage, so it is clear which turn is meant.

Arrows

a -> b means a, then b. A line may be as long as you like: advocate -> critic -> judge. Every arrow needs a step on each side: advocate -> -> judge is refused.

Lines that join

Lines join where one ends and the next begins. a -> b -> c and c -> d -> e, in either order, are a -> b -> c -> d -> e; two lines of one block join the same way. So a flow has one first step, and each step goes on to one next step. Refused:

  • two lines going on from the same step (advocate -> critic, critic -> judge, critic -> fact_checker): to choose between two next steps, the step decides;
  • two lines leading into the same step;
  • lines that do not join up (advocate -> critic and judge -> fact_checker), including two lines that start at the same step;
  • lines that go round in a circle: a loop is a decision;
  • a line joining at a member who takes several turns in the flow, without a stage to say which;
  • a joint written with two different counts (advocate -> rounds(*2) and rounds(*3) -> judge).

Named blocks

name = … defines a block: a part of the flow with a name, used as a step. Blocks may use other blocks.

rounds(*3) -> judge
rounds = advocate_turn -> critic_turn
advocate_turn = advocate -> fact_checker
  • A block's name may not be a member's name.
  • A block with nothing after the = is refused.
  • A block that runs itself, directly or through another block, is refused: use (*N) to repeat it.
  • A block that the flow never uses is a warning.
  • A file with blocks but no main line is refused, "this chair.md has no flow".

Repeats

name(*N) runs a step or a block exactly N times, N 1 or more: rounds(*3), critic(*2). Nothing inside a repeat decides to leave it early; for "until it passes, at most three times", use a decision with a count. (3) and (*0) are refused: write (*3). A repeated step cannot decide, and a decision cannot point to a repeat.

Decisions

A member whose file declares a choice under output: can decide where the flow goes. Give the debate a fact checker, fact_checker.md, with verdict: [pass, fail] under its output:, and wire its answer into the script:

# Three rounds. Each speech is fact-checked; a failed speech gets two
# more tries, then the debate moves on. Then the judge decides.

rounds(*3) -> judge

rounds = advocate_turn -> critic_turn

advocate_turn = advocate -> fact_checker
                fact_checker --fail--> advocate
                fact_checker --pass,*3--> done

critic_turn = critic -> fact_checker
              fact_checker --fail--> critic
              fact_checker --pass,*3--> done

fact_checker --fail--> advocate means: when the fact checker answers fail, go back to the advocate. The member's file says how to decide; the flow says what each answer means here. That is why one fact checker can check both sides.

  • Every option needs exactly one arrow, and every arrow must be one of the options. A typo is refused with the nearest option (--puss--> → did you mean pass?); an option with no arrow is refused, naming it; two arrows for one option are refused.
  • One arrow may carry several options, separated by commas: --pass,*3-->. An option is one word.
  • Only a member decides: not a block, not a toolkeeper, not done or stop. A member that decides must declare a choice in its file; when it has several, the arrows' options must fit exactly one of them.
  • Where a decision goes. A decision on a line of its own belongs where its decider takes a turn. If the decider takes turns in several blocks, as the fact checker does here, it belongs with the nearest line above it that holds the decider; with none above, it is refused. If the decider takes more than one turn in that block, give the turns stages.
  • Inside a line. A labelled arrow may also sit inside a line of steps. This says the same as the blocks above:

advocate_turn = advocate -> fact_checker --pass,*3--> done fact_checker --fail--> advocate

  • An arrow to a step not in any line (reviewer --pass--> critic:reply) adds that step, reached only by the decision. After it, its block ends.

Each decision is logged in the run: who decided, the answer, where the flow went, and how many times the decider had decided there.

Loops and counts

An arrow back to an earlier step, or to the decider itself, is a loop. A loop needs a counted way out: some arrow from the same decider must carry *N, "the Nth time". Without one it is refused, so every flow ends.

  • fact_checker --pass,*3--> done reads "on pass, or the third time, go to done". On the third time the decider's answer still counts if it leaves the loop: a pass on the third try is a pass. Only an answer that would go round again is overridden.
  • To have running out go somewhere else, give the count its own arrow: fact_checker --*3--> stop. Here a third failure ends the run.
  • A decider has one counted way out; two are refused. The counted arrow must point forward, to a later step, done or stop: one that loops back too is refused.
  • The count is per decider, within the current run of its block, so each round starts afresh. In the run, the second and third tries show as "try 2 of 3".

done and stop

done ends the block it is in, and the flow carries on after the block. In the main line it ends the run, as reaching the end of the flow does. In the fact-checked debate, --pass,*3--> done ends advocate_turn only: the speaker's turn is over and the debate goes on.

stop ends the whole run at once. The run's record says it was stopped by the flow, and which answer led there. done and stop take no stage or count, and nothing may come after them in a line.

Comments

# and everything after it on a line is a note, for anyone reading the file. Notes are a good place to say what the flow is for and why it is written this way; the shipped examples do.

Toolkeeper steps

A toolkeeper is usually asked as a side trip, in a member's own turn, and the flow does not mention it. When asking must happen, make the toolkeeper a step:

rounds(*3) -> judge:research -> web -> judge:verdict

The member just before the toolkeeper must end its turn with a request to it. The toolkeeper replies to that member alone, who reads the reply at its next step; that is why the judge comes again after web. Nothing in the line marks web as a toolkeeper: its own file does. explain --diagram draws toolkeeper steps in a shape of their own.

What validate refuses

teamrunner validate checks the flow against the team, and names the line of each problem.

Writing the lines

  • A line starting with an arrow, with no line above it to continue.
  • A one-dash typo in a continued line: --pass-> c, meant as --pass-->, is refused and the fix suggested. New in 0.0.7. Inside a line, a broken arrow is refused as "this decision should read decider --option--> step".
  • An empty label (---->), a label that is not one word (--pass or fail-->), or a step missing between two arrows.
  • A step that is not a name, name:stage or name(*3) (critic!).
  • A count that is not (*N) with N 1 or more.
  • Anything after done or stop in a line, or a stage or count on them.
  • A block with no steps, a file with no main line, or a setting in the settings block.

Joining lines

  • Two lines going on from one step, two leading into one step, lines that do not join up, lines in a circle.
  • A line or decision naming a member who takes several turns there, without a stage.
  • A joint written with two different counts.
  • A block named like a member, or a block that runs itself.

Decisions and loops

  • A decision whose decider takes no turn anywhere in the flow, or takes turns in several blocks with none of its lines above the decision.
  • A decider that is a block or a toolkeeper, or a member whose file declares no options.
  • An option that is not the decider's (with the nearest), an option with no arrow, two arrows for one option, or options fitting more than one of its outputs.
  • A counted way out with no options beside it.
  • A loop with no counted way out; two counted ways out; a counted way out that loops back.
  • A repeated step that decides, or a decision that points to a repeat.

Toolkeepers in the flow

  • A toolkeeper as the first step, or just after a block or another toolkeeper: a member must ask it.
  • A repeated toolkeeper step (web(*2)).
  • A member asking it who is not let in by its access:. The fix says which line to add.
  • A member who decides at that step: its turn cannot also end with a request. The fix gives the request a turn of its own: fact_checker:ask -> web -> fact_checker.
  • A repeated turn just before a toolkeeper: in judge:research(*2) -> web, only the last turn's request would reach web. The fix shows a repeated block that asks each time: judge_research(*2) with judge_research = judge:research -> web. New in 0.0.7.
  • A decision arrow to a toolkeeper. In a -> web -> b with b --again--> web, b only decided, so web would have no request to answer. The fix points the arrow at the member who asks (b --again--> a), after whom the flow goes through web again. New in 0.0.7. A decision to a toolkeeper that is in no line is refused too: the member before it must ask it.

Warnings

These do not stop a run:

  • A member with a model that never takes a turn in the flow.
  • A block that is never used.
  • A toolkeeper whose reply goes to the member who asked, while someone else speaks next (programmer -> sandbox -> reviewer): the reviewer does not get the reply. If it needs the result, let the asker pass it on.

Not yet: members working at the same time (a -> [b, c]), a loop that leaves on a condition (talks(deal is agreed, *12)), a chair that is a decision table (kind: rules), and a team run by a model's judgment (manager.md, in place of chair.md) come in a later version of TeamRunner; validate refuses each, and a team with both chair.md and manager.md is refused.
