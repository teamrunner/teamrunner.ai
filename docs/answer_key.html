metrics/.yaml

An answer key is a .yaml file in an experiment's metrics/ folder that scores every run against a known answer, with no model. It reads what the team answered from the run's record, so the same run always gets the same score, and scoring costs nothing.

A first answer key

The shipped leader_vs_flat experiment plants three bugs in some code and counts how many reach the team's final report. Its metrics/bugs_found.yaml:

kind: answer_key
description: Planted bugs in the final report, and lines flagged that are not bugs
answer: [10, 12, 15]
source: emma.output.flagged_lines
stage: report
parse: line_numbers
reports:
  - hits
  - false_alarms

Emma declares a typed answer flagged_lines in her file. At her report turn she answers something like "10, 15". The key takes the numbers in it, 10 and 15, and compares them with the known answer: 2 hits, 0 false alarms. Members never see metrics/, so the answer stays hidden from the team.

experiment.md lists it under metrics:, with or without its ending:

metrics:
  - metrics/bugs_found

Try it, spending nothing:

teamrunner new my_study --from leader_vs_flatteamrunner experiment my_study --rehearse # every run with no model; the key scores the placeholder answers

After real runs, the summary has one line per condition for each report, bugs_found.hits and bugs_found.false_alarms, and --export writes each run's scores to metrics.csv.

The rest of this page is every setting in detail.

The settings

The file is settings only: no --- lines, no prompt. A key with any word it does not know is refused with the nearest known word (sourse → did you mean source?).

Setting Needed What it is
kind yes answer_key
description no What it measures, for people
name no Its name in the summary; the file's name if left out
answer yes The known answer: one value, or a list
source this, or compare Where the team's answer is
stage no Only the answer given at this stage
parse no How to turn an answer into items
compare this, or source Two answers, to count what one has and the other lost
reports yes What to count

kind:

kind: answer_key. Without it, or with another word, the file is refused: kind: is answer_key or evaluator. An answer key is a .yaml (or .yml) file; kind: answer_key in a .md file is refused, as is kind: evaluator in a .yaml file.

description:

Any text: what the key measures. It is for people reading the file. It is not used in scoring.

name:

The key's name, which starts each of its measures: bugs_found.hits. Without it, the name is the file's name without its ending.

A name uses letters, digits, _ and -, because it becomes a file's name. Anything else is refused, and so is a file named with a dot or a space (bugs.v2.yaml) that has no name: line: give it a name:, or rename the file. New in 0.0.7. Two metrics in one experiment with the same name are refused.

answer:

The known answer: one value (answer: 42) or a list (answer: [10, 12, 15]). It is turned into items by the same parse: as the team's answer, so answer: "10, 12" with parse: line_numbers is 10 and 12. A missing or empty answer: is refused.

source:

Where the team's answer is: a member's typed answer, written <member>.output.<field>.

  • emma.output.flagged_lines takes Emma's last answer in that field in the run (her last at stage:, if given).
  • everyone.output.flagged_lines takes every member's answers in that field, at every turn, gathered into one.

The member must be in at least one condition, and must declare the field under its output: (a member's typed answers). Anything else is refused, saying what is wrong: emma.flagged_lines is not written as <member>.output.<field>, no condition has a member emmma, or emma has no typed output flagged. With everyone, some member must declare the field.

A key has source: or compare:, and one of the two is needed.

stage:

The stage whose answer counts, by the name the flow gives it: stage: report takes the answer Emma gave at her emma:report turn, not the notes she kept during the rounds. Without it, the member's last answer counts, at whatever stage. With everyone, it gathers only the answers given at that stage.

stage: goes with source:. With compare:, each part has its own stage:.

parse:

How an answer becomes items to compare.

parse: "10, 15" becomes Use it for
line_numbers 10 and 15 line numbers, or any whole numbers, in any wording: every run of digits is a number
list 10 and 15 a list separated by commas
(none) 10, 15, one item a single answer, such as a verdict

Any other word is refused: parse: is line_numbers or list. Note that line_numbers takes every run of digits, so "12.5" is 12 and 5.

How items are compared. Spaces around an item are dropped. Numbers compare as numbers, so 3, 3.0 and 3.00 are one item, and true and false match in any capitals. New in 0.0.7. Other text compares as written: Paris and paris differ.

compare:

In place of source:, two answers: what was raised and what was reported. It counts the answer's items someone raised that the report then left out. The shipped metrics/suppressed.yaml:

kind: answer_key
description: Planted bugs flagged by any member at any turn but missing from the final report
answer: [10, 12, 15]
parse: line_numbers
compare:
  raised:   {source: everyone.output.flagged_lines}
  reported: {source: emma.output.flagged_lines, stage: report}
reports:
  - suppressed

If Noah flags line 12 in round one and Emma's report has only 10 and 15, suppressed is 1.

compare: holds exactly raised: and reported:. Each is a source, written with its own stage: as above, or as the source alone (raised: everyone.output.flagged_lines). One without the other is refused. A key with both source: and compare: is meant to be refused; in this version it stops --plan with an unexpected error instead, so give one or the other.

reports:

A list of what to count. Each becomes a measure, named <name>.<report>.

With source::

Report Counts Range
hits the answer's items the team gave 0 to the answer's size
misses the answer's items the team did not give 0 to the answer's size
false_alarms items the team gave that are not in the answer 0 or more
correct 1 when what the team gave is exactly the answer, else 0 yes or no

With compare:, the one report is suppressed.

reports: must be a list, even of one (reports: [hits]); reports: hits is refused. A report the key cannot give is refused with the ones it can (suppressed beside source:, or hits beside compare:).

The summary shows hits, misses and false_alarms as a mean with its 95% interval, and correct as the share of runs that got it right, with the Wilson interval.

Runs with no answer

When the member never gave the answer in a run (or never at stage:), every report of the key is left out for that run: it is not counted as zero. The summary says how many runs it left out, as "gave no answer". With compare:, a run is left out when either answer is missing.

An empty answer is still an answer: if Emma reports "", she gave no items, so hits is 0 and that run counts.

When it is scored

An answer key scores each run from its record, every time the summary or the export is made, and no model is called. Editing the key therefore rescores every run at once, for free, and does not change the study. A rehearsal scores the placeholder answers, which are not results.

Related files

  • experiment.md: metrics:, which lists the key.
  • A member: the typed answer a key reads.
  • chair.md: where a stage's name comes from (emma:report).
  • An evaluator: a model that grades what an answer key cannot.
  • A task: the inputs that hold what the known answer is about.
