variants/

A variant is a file in an experiment's variants/ folder that a condition puts in place of one of the team's: a whole member, a member's prompt, the chair's flow, a model profile, or the text of one setting. The team itself is never edited; the variant goes into the condition's own copy of it.

A first variant

The shipped leader_vs_flat experiment gives Emma a leader's prompt in one condition. Its variants/emma_leader.md holds the prompt only, with no settings block:

You are Emma, the team leader of a five-person code review team
(you, Noah, Lily, Derek and Zoe). The team is reviewing this function
against its specification, and you are accountable for the result.

Specification:

{{spec}}

Code:

{{code}}
…

and experiment.md names it under the condition's change::

  visible_leader:
    from: orchestrators_lite
    change:
      chair: file:variants/chair_leader.md
      emma.prompt: file:variants/emma_leader.md

visible_leader gets Emma's settings as they are, with this text as her prompt. Try it, spending nothing:

teamrunner new my_study --from leader_vs_flatteamrunner experiment my_study --plan

--plan lists every file a variant changed, condition by condition:

flat → visible_leader:
  chair.md                 changed  replaced by variants/chair_leader.md (flow changed)
  emma.md                  changed  prompt from variants/emma_leader.md

The rest of this page is what each kind of variant must hold.

The five kinds

What a variant file must contain depends on the line in change: that names it.

change: line The variant is It must hold
judge: file:variants/strict_judge.md a whole member a member file: settings block and prompt
emma.prompt: file:variants/emma_leader.md a prompt the prompt only, no settings block
chair: file:variants/chair_leader.md a chair flow a flow, as in chair.md
models/careful: file:variants/careful.yaml a model profile a model profile: name: and params:
lily.description: file:variants/long.txt a setting's text the setting's new value, as plain text

Every variant is named with file: and its path from the experiment's folder. It must be inside that folder; variants/ is where it usually goes. A path that names no file there is refused with the nearest file in variants/ (file:variants/nope.md → did you mean file:variants/noah2.md?). A file outside the experiment's folder is refused.

After the variants are in place, each condition is checked as a whole team, as teamrunner validate would, so a problem in a variant is shown at the file and line where it landed in the condition's copy under conditions/<name>/.

A whole member

A whole member file, written as any member is: a settings block between two --- lines, then the prompt.

---
description: A strict reviewer
output:
  flagged_lines: ""
---
You are Noah, a strict reviewer. …

noah: file:variants/noah_strict.md replaces the team's noah.md with it. If the team has no member of that name, the variant adds one: quinn: file:variants/quinn.md gives the condition a sixth member (put quinn in the flow too, or --plan warns that quinn never takes a turn). A toolkeeper (kind: toolkeeper) is replaced or added the same way.

  • The settings block is needed. A file without one is a note, not a member, so the condition would lose the member and its flow would be refused: noah is not a member of this team.
  • No name:. A member is named by its file, and here by the word before the : in change:; a name: line is refused, as in any member file.
  • Every setting is checked as a member's is. A model written without its provider (model: gpt5) is refused, and so is a params: word outside the model settings list. New in 0.0.7.
  • Inputs. A placeholder the team does not have ({{topic}}) must come from the experiment's task or the team's default_inputs:, or the condition is refused.
  • With setting changes. Whole files are put in first, so judge: file:… beside judge.model: … gives the new judge that model.

A prompt

The member's new prompt: the text below the settings block, and nothing else.

You are Zoe. Review this code briefly:

{{code}}

zoe.prompt: file:variants/zoe_prompt.md keeps Zoe's settings and puts this text below them.

  • No settings block. A prompt file that starts with --- is refused: zoe.prompt takes a prompt, but this file starts with a settings block. To change the settings too, change the whole member (zoe: file:…), or change each setting on its own line (zoe.model: …).
  • A file, not the text itself. zoe.prompt: Just say hi is refused; the prompt goes in a file.
  • Placeholders work as in any prompt. One the team does not have must come from the task or default_inputs:, or the condition is refused: c needs the input topic, which neither the task nor the team gives.
  • The file can have any ending: .md and .txt both work.

A chair flow

A flow, written as in chair.md:

# The VISIBLE LEADER condition.
emma:kickoff -> review_rounds(*3) -> emma:report

review_rounds = noah -> lily -> derek -> zoe -> emma:summary

chair: file:variants/chair_leader.md replaces the team's whole chair.md; there is no chair.<setting>. Its flow is checked as the team's would be: a name the team has no member or block for is refused, and a member who never takes a turn is a warning.

A model profile

A whole model profile:

name: anthropic/claude-haiku-5-5
params:
  max_tokens: 4096
  temperature: 1.0

models/engineer: file:variants/engineer_hot.yaml replaces the team's models/engineer.yaml, so every member that uses that profile gets the new settings. The name can be written with or without .yaml. A profile the team lacks is added (models/fast: file:…); a misspelled one is refused with the nearest (models/engneer → did you mean models/engineer?). Its params: take the model settings list only. New in 0.0.7.

A setting's text

Plain text, which becomes one setting's value.

lily.description: file:variants/lily_desc.txt gives Lily's description: the file's text. The whole file is the value, a final line break included, so it suits text settings such as description:. For a short value, write it in change: itself (lily.model: openai/gpt-5).

How a variant is named

Nothing in a variant names where it goes: the line in change: does. The variant's own file name is yours to choose, and it lands in the condition's copy under the name the change gives it:

change: line Lands in conditions/<name>/ as
noah: file:variants/noah_strict.md noah.md
emma.prompt: file:variants/emma_leader.md the prompt of emma.md
chair: file:variants/chair_leader.md chair.md
models/engineer: file:variants/engineer_hot.yaml models/engineer.yaml
lily.description: file:variants/lily_desc.txt description: in lily.md

One variant can serve several conditions or factor levels.

Ids written into variants

Before an experiment runs (teamrunner experiment <name>, and --rehearse too), TeamRunner writes an id: line into every whole-member variant that has none, in the variant file itself:

  • A variant that replaces a member takes that member's id: it is a new version of the same member, so its history stays together.
  • A variant that adds a member gets a new id.
---
id: 01M73WPYPH9N91EPE1HZ4327XX  # added by teamrunner — keeps this agent's history together
description: A strict reviewer

A variant that already has an id keeps it. Prompt, flow, profile and text variants get none. --plan writes no ids. Ids are left out of the study's fingerprint, so writing them changes no study. If an id cannot go into a file without breaking it, the file is left exactly as it was. New in 0.0.7.

Editing a variant

A variant is part of the condition it is in: editing it changes that condition's fingerprint, and the next command stops and says what changed (see what changes the study). Edit variants here, not in conditions/, which is rebuilt before every run.

The experiment's folder, variants/ included, is checked for API keys as a team's is, and a key found there is refused. New in 0.0.7.
