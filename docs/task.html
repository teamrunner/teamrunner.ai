tasks/.yaml

A task file gives a team its inputs by name, all at once: the topic, the code to review, the document to check. It lives outside the team, in an experiment's tasks/ folder or anywhere you keep your jobs, so the team's own default_inputs: stay as they are.

A first task

A team whose prompts use {{spec}} and {{code}} takes two inputs. This file gives both:

name: order_summary
description: A 17-line Python function with three planted defects
inputs:
  spec: >
    summarize_orders(orders, discount_rate) returns the total revenue,
    the average order value, and the largest order amount, counting only
    orders whose status is "paid".
  code: |
    1  def summarize_orders(orders, discount_rate=0.1):
    2      ...

Give it to one run:

teamrunner run orchestrators_lite --task-file tasks/order_summary.yaml --rehearse # no model, no costteamrunner run orchestrators_lite --task-file tasks/order_summary.yaml

The run's first line says where each input came from: given input code: "…" · default input spec: "…".

Or give it to every condition of an experiment, with one line in experiment.md:

task: tasks/order_summary

The shipped leader_vs_flat experiment does this: teamrunner new my_study --from leader_vs_flat.

The rest of this page is every setting in detail.

The settings

A task file is settings only, in YAML. Any word besides these three is refused: a task file holds inputs:, and may have a name: and a description:.

Setting Needed What it is
name no A label for people
description no What the task is, for people
inputs yes One line for each input: its name, then its value

name:

A line of text: name: order_summary. It is a label for people reading the file. It is never sent to a model and is not part of an experiment's study, so renaming it changes nothing. Anything but text (name: [a]) is refused.

description:

A line of text, as name: is: what the task is, where it came from. It is never sent to a model and is not part of the study.

inputs:

One line for each input: the input's name, as the team's prompts write it between braces, then its value. {{spec}} in a prompt is filled by spec: here.

inputs:
  topic: "Should cities ban cars downtown?"
  audience: city council

Long text reads best as a YAML block: | keeps the line breaks (code, a numbered list), > joins the lines into one paragraph.

  • inputs: is needed, and holds names and values. A file without it, or with a list under it, is refused: it should hold inputs:, with one name: value line under it for each input.
  • Every name must be an input the team uses. A name no prompt uses is refused before anything is spent: the task gives topic, but no prompt in orchestrators_lite uses it, and the message lists the team's inputs.
  • Only what you want to give. An input the task leaves out comes from the team's default_inputs:.

How a task meets the team's defaults

A team's prompts decide what inputs it takes; default_inputs: in team.yaml gives some or all of them a value. A task file fills inputs by name, in place of those defaults:

The input is Its value
in the task the task's
not in the task, but in default_inputs: the default
in neither none: the run is refused before anything is spent

A run with an input in neither stops with what is needed: the team needs topic, which has no default; give it with --message, --file or --task-file, or add it under default_inputs:. Every input is recorded in the run's record.json as given or default.

teamrunner run --task-file

teamrunner run <team> --task-file <path> gives one run the task's inputs. The path is from where you are, or from your home folder if it starts with ~; a path with no file is refused.

--message and --file go with it: they fill the one input message_goes_to: names, and the task fills the rest. The same input given by both is refused: code is given twice, by --message and by the task file.

In an experiment

task: in experiment.md names a task file by its path from the experiment's folder, with or without its ending (.yaml or .yml): task: tasks/order_summary. A name with no file is refused with the nearest file in tasks/ (tasks/order_sumary → did you mean tasks/order_summary?).

Every condition then gets the same inputs, so an edit to the team's default_inputs: cannot change the task. The rules above apply to each condition: an input the task gives must be one that condition's prompts use, and an input a condition needs must come from the task or that team's defaults. A variant prompt that adds a placeholder needs its input here.

The task's inputs are part of each condition's study: editing a value changes the study, and the next command stops and says what changed (see what changes the study). name: and description: are not part of it.

A task file is never part of a team. Members see an input only through the prompts that use it; they never read the file, or metrics/ beside it.

The experiment's folder, tasks/ included, is checked for API keys as a team's is, and a key found there is refused. New in 0.0.7.

Related files

  • team.yaml: default_inputs: and message_goes_to:.
  • experiment.md: task:, which gives every condition the task.
  • A member: the prompts whose placeholders name the inputs.
  • An evaluator: reads an input with {{inputs.<name>}}.
  • An answer key: the known answer the task's inputs are about.
